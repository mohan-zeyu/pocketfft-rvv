# pocketfft-RVV: RISC-V Vector (RVV 1.0) acceleration of pocketfft

pocketfft (`pocketfft_hdronly.h`, Martin Reinecke, BSD-3-Clause) is the header-only C++ FFT that NumPy
(`numpy.fft`), PyTorch CPU (`torch.fft`, on every build without MKL, i.e. all of RISC-V) and ITK vendor. On RISC-V
every single 1-D transform it executes is scalar: upstream only vectorises batched lines through a 256-bit
compiler-generated vector type, and NumPy/PyTorch pin commits older than even that. This repository adds a
**vector-length-agnostic, runtime-dispatched RVV 1.0 intrinsics backend** for the single 1-D transforms:

* complex radix-2/3/4/5/8 passes and real (half-complex) radix-2/3/4/5 passes, vectorised across butterflies with
  nf=2 segment loads/stores (split re/im in registers), no `vrgather`, no shuffles;
* vectorised twiddle generation (NumPy and PyTorch rebuild the plan on every call), RVV buffer copies and
  half-complex pack/unpack;
* one binary for every VLEN (128/256/512 tested; all loops use `vsetvl`), `getauxval(AT_HWCAP)` run-time check,
  unchanged code on every other ISA, no API change, results equal to the scalar build up to rounding
  (about 1e-17 relative in double).

Measured under QEMU (dynamic instructions per transform, double c2c, clang 23; a trend indicator, not a time):
the kernel NumPy executes per row needs **2.2x / 4.3x / 8.3x fewer instructions at VLEN 128 / 256 / 512** for
n = 4096 and 2.4x / 4.8x / 9.6x for n = 65,536; the public `pocketfft::c2c` call without plan cache 2.0-5.1x fewer
at VLEN 256; `r2c` up to 7.9x. The same library compiled for x86-64 (AVX2) and aarch64 (NEON) runs the scalar 1-D
path, 3.7-4x more instructions than the RVV build at VLEN 256. Correctness: max relative error 1.5e-16 (double) /
6.4e-8 (float) against NumPy 2.5.3, 1.3e-15 / 3.6e-7 against FFTW 3.3.11, at every VLEN with both compilers.
Hardware timing on a board is the remaining step (`docs/hardware-run-guide.md`).

## Using the header

Drop-in: replace the vendored `pocketfft_hdronly.h` by `dist/pocketfft_hdronly_rvv.h` (or copy the three files
next to each other). Nothing else changes. The RVV paths compile in when the ISA string contains V
(`-march=rv64gcv...` or an RVA23 toolchain default) and the compiler offers the frozen intrinsics API
(GCC >= 14, clang >= 17; `__riscv_v_intrinsic >= 12000`); at run time they are used when the kernel reports V in
`AT_HWCAP`. Macros: `POCKETFFT_NO_RVV` (compile the paths out), `POCKETFFT_RVV_LMUL{2,3,4,5,8}` /
`POCKETFFT_RVV_RLMUL{2,3,4,5,_EDGE}` (LMUL per radix), `POCKETFFT_RVV_NOSCHED` (GCC-only
`optimize("no-schedule-insns")` attribute on the pass entry points; define empty to disable),
`POCKETFFT_RVV_SPLIT_STORE` (0; experiment), and pocketfft's own `POCKETFFT_CACHE_SIZE` (0 in NumPy/PyTorch;
16 saves 25-35 % of the per-call cost for repeated lengths, see `docs/design.md` section 8).

## Building and running

Toolchains used (`scripts/common.sh`): clang 23.1.6 (apt.llvm.org, recommended), GCC 15.3 (bootlin 2026.08-1 at
`/opt/riscv-gcc-bootlin`), QEMU 11.1.3 with TCG plugins at `/opt/qemu` (`libinsn.so` from the QEMU build tree,
`librvvclass.so` from `/home/user/harness/plugins`), NumPy 2.5.3 on the x86 host.

```sh
# all variants (x86-64, aarch64, riscv64 gcc15/clang23 x rvv/scalar/autovec) -> build/<variant>/{fft_check,fft_bench}
scripts/build.sh

# by hand, clang 23, VLEN-agnostic RVV build (static: runs under qemu-riscv64 and on any rv64gcv Linux board)
clang++-23 --target=riscv64-linux-gnu --gcc-toolchain=/usr -isystem /usr/riscv64-linux-gnu/include \
  -isystem /usr/riscv64-linux-gnu/include/c++/13 -isystem /usr/riscv64-linux-gnu/include/c++/13/riscv64-linux-gnu \
  -fuse-ld=lld -static -O3 -std=c++17 -march=rv64gcv_zba_zbb_zbs -I. bench/fft_bench.cpp -o fft_bench_rvv
# scalar baseline: same command with -march=rv64gc_zba_zbb_zbs -DPOCKETFFT_NO_RVV
# GCC 15:
/opt/riscv-gcc-bootlin/bin/riscv64-linux-g++ -static -O3 -std=c++17 -march=rv64gcv_zba_zbb_zbs -I. bench/fft_bench.cpp -o fft_bench_rvv_gcc

# run under QEMU at a chosen VLEN (128 / 256 / 512 / 1024)
/opt/qemu/bin/qemu-riscv64 -cpu rv64,v=true,vlen=256,elen=64,zba=true,zbb=true,zbs=true ./fft_bench_rvv --type double --kind c2c-fwd --n 4096 --trials 1

# correctness: FFTW oracle (1080 cases per configuration), RVV at 3 VLENs compared with the scalar dump
scripts/run_correctness.sh --quick            # n <= 4096, 1-2 min; without --quick up to n = 2^20
# correctness: NumPy oracle on one transform
/opt/qemu/bin/qemu-riscv64 -cpu rv64,v=true,vlen=256 build/c0_rvv_clang c2c double 1000 1 /tmp/x && python3 tests/compare_numpy.py c2c double 1000 1 /tmp/x

# instruction counts (QEMU libinsn plugin, (11 reps - 1 rep) / 10)
scripts/insncount.sh build/c16_rvv_clang 256 x2c double 4096     # kernel (plan cached, in place)
scripts/insncount.sh build/c0_rvv_clang 256 c2c double 4096      # public API without plan cache
scripts/measure_all.sh                                           # full matrix -> results/final_insns.csv
scripts/run_bench_qemu.sh --quick                                # fft_bench sweep with vector share -> results/bench_qemu.csv
python3 docs/gen_tables.py                                       # regenerate the tables in docs/performance-report.md

# on a RISC-V board (see docs/hardware-run-guide.md for governor, pinning, perf)
taskset -c 2 ./fft_check_rvv --csv board.csv && taskset -c 2 ./fft_bench_rvv --type double --kind c2c-fwd --n 65536 --trials 11
```

## Status and known limitations

Vectorised: complex passes radix 2/3/4/5/8, real passes radix 2/3/4/5, twiddle generation, contiguous copies,
half-complex pack/unpack, scaling. Scalar (unchanged): radix 7/11 and generic-radix passes, Bluestein's chirp
multiplications (its embedded power-of-two FFTs use the RVV passes), DCT/DST front-ends, the batched
generic-vector path (compiler-generated), `long double`. GCC 15 output is correct; it is ~1.4x the instruction count of
clang's on the complex kernel but on par or better for real transforms and small sizes. Numbers in this repository are QEMU instruction counts; see
`docs/performance-report.md` section 1.4 for what they do and do not say and section 8 for the board procedure.
