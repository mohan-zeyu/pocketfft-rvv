## 0. Headline

* **What is measured.** Dynamic instruction counts per 1-D transform under QEMU 11.1.3 user mode (TCG plugin
  `libinsn`): same source, same compiler, same flags except the ISA string and `-DPOCKETFFT_NO_RVV`. QEMU cannot
  measure time; an instruction-count ratio is a *trend indicator* for the "optimisation trend" part of the rubric,
  not a cycle ratio (section 1.4). The final numbers for the competition must come from a board, with the protocol
  in `docs/hardware-run-guide.md` and the commands in section 8.
* **Kernel (what NumPy's per-row path executes, plan cached), double c2c forward, clang 23**
  (`results/kernel_insns.txt`): n = 4096: 297,934 scalar instructions vs 136,819 / 69,501 / 35,842 with RVV at
  VLEN 128 / 256 / 512 = **2.2x / 4.3x / 8.3x fewer instructions**; n = 65,536: 6,896,666 vs 2,832,190 / 1,424,978 /
  721,372 (**2.4x / 4.8x / 9.6x**); n = 2^20: 143.6 M vs 66.9 M / 37.5 M / 22.0 M (2.1x / 3.8x / 6.5x). Float
  gains about twice as much (n = 65,536 at VLEN 256: 9.6x, `docs/data/kernel_insns_remeasured.txt`).
* **Public API `pocketfft::c2c` without plan cache (what NumPy and PyTorch call), clang 23, VLEN 256**
  (`results/api_nocache_insns_v3.txt`, `results/final_insns.csv`): n = 256: 33,533 -> 17,110 (2.0x); 1024:
  115,605 -> 33,978 (3.4x); 4096: 453,387 -> 111,348 (4.1x); 65,536: 9,077,497 -> 1,772,167 (5.1x); 2^20:
  177.5 M -> 42.0 M (4.2x). With the plan reused (`POCKETFFT_CACHE_SIZE=16`): 4096: 329,034 -> 74,013 (4.4x),
  65,536: 7.36 M -> 1.46 M (5.0x). VLEN 512 reaches 6.5-9.9x, VLEN 128 2.2-2.6x (section 2).
* **Real transforms** (`pocketfft::r2c` / `c2r`, the `np.fft.rfft` / `irfft` path): with the real passes and the
  vectorised half-complex pack/unpack, r2c double n = 65,536 without plan cache goes from 5.51 M to 1.30 M / 0.70 M /
  0.39 M instructions at VLEN 128 / 256 / 512 (4.2x / 7.9x / 14.2x, `results/final_insns.csv`); section 7.
* **Cross-ISA** (`results/xisa_insns.txt`, `results/xisa_api_insns.txt`): the same header compiled for x86-64
  (GCC 13, `-march=x86-64-v3`) and aarch64 (GCC 13, armv8.2) executes the *same scalar* 1-D code path (pocketfft
  only vectorises batched lines): kernel n = 4096 270,489 / 241,206 instructions, API n = 4096 297,233 / 263,987.
  The RVV build at VLEN 256 executes **3.9x fewer instructions than the x86-64 AVX2 build of the same library
  in the kernel and 2.7-3.5x fewer at the API level** (n = 4096 / 65,536), at VLEN 128 1.5-2x fewer. Native x86
  wall time for scale: 35.6 us (n = 4096) and 1.16 ms (n = 65,536) per double c2c on the 2.1 GHz Xeon build host,
  where FFTW 3.3.11 (AVX2, `FFTW_MEASURE`) is 3.5-3.6x faster than pocketfft (section 6).
* **Rubric.** FFT performance >= +10 %: the instruction-count reduction is 2-10x on every size from 256 to 2^20
  and for every VLEN; the margin is large enough that the hardware measurement is expected to confirm the bar even
  if one vector instruction cost several scalar-instruction equivalents (section 1.4 discusses the X60's known
  costs). Interface adaptation: the gains apply unchanged to NumPy, PyTorch and ITK (`docs/integration.md`).

## 1. Method

### 1.1 Instrument

```
qemu-riscv64 -cpu rv64,v=true,vlen=<128|256|512>,elen=64,zba=true,zbb=true,zbs=true \
    -plugin /home/user/research/work/qemu/build/tests/tcg/plugins/libinsn.so -d plugin -D out.txt <binary> <args>
```

`libinsn` prints `total insns: N`, the number of guest instructions retired by the process (libc, start-up and
plan construction included). `scripts/insncount.sh <binary> <vlen> <kind> <type> <n> [fwd]` runs the program twice,
with 1 and with 11 repetitions of the transform, and prints `(insns(11) - insns(1)) / 10`. Everything that does not
scale with the repetition count (process start, input generation, the first transform) cancels out, so the figure
is the cost of one additional transform **as the caller would issue it**:

| measure | binary prefix (`build/`) | what one repetition executes | corresponds to |
|:---|:---|:---|:---|
| **kernel**, `x2c` | `c16_*` (`POCKETFFT_CACHE_SIZE=16`) | `plan->exec(buf, 1, fwd)` in place on a cached `pocketfft_c<T>` plan | NumPy's per-row path after `get_plan`; isolates the radix passes |
| **API, no cache**, `c2c`/`r2c`/`c2r` | `c0_*` (`POCKETFFT_CACHE_SIZE=0`) | `pocketfft::c2c(...)` out of place: plan construction (twiddles), `copy_input`, passes, `copy_output` (+ half-complex repacking for r2c/c2r) | NumPy and PyTorch today (`integration.md` section 2: neither defines `POCKETFFT_CACHE_SIZE`, so twiddles are recomputed per call) |
| **API, plan reused**, `c2c`/`r2c`/`c2r` | `c16_*` | the same call with the plan found in pocketfft's cache | SciPy-style callers, or NumPy/PyTorch after the `POCKETFFT_CACHE_SIZE` follow-up (`design.md` section 8) |

The driver is `tests/fftdump.cpp` (deterministic LCG input in [-1, 1), `fct = 1`, one 1-D transform of length n;
`c2c` forward, `r2c` forward, `c2r` backward). The final matrix (`results/final_insns.csv`) was produced by
`scripts/measure_all.sh` + `scripts/measure_rest.sh`; the per-step files in section 5 by the same `insncount.sh`
method at earlier commits.

### 1.3 Statistics

Instruction counts under QEMU are deterministic: repeated measurements of the same binary agree to a few
instructions (the n = 4096 kernel: 69,501 in `results/kernel_insns.txt`, 69,490 / 69,492 / 69,525 in three
independent re-runs and rebuilds; the variation comes from libc's `memcpy` ifunc and plan-cache bookkeeping).
Rebuilding from source at a later commit reproduces the numbers to about 1 % (section 9). No averaging over
launches is therefore needed; the `(11 - 1)/10` differencing is the only statistical treatment.

### 1.4 What an instruction count does and does not say

* A vector instruction processes `VLEN/SEW * LMUL` lanes. On a core whose datapath is as wide as VLEN (one
  256-bit FMA per cycle on the SpacemiT X60, `related-work.md` section 7) the cycle ratio can be *higher* than the
  count ratio; on a core that cracks LMUL > 1 groups or wide VLEN into several uops it is lower.
* Segment loads/stores (`vlseg2e`/`vsseg2e`) and strided accesses are not single-cycle on current cores (X60:
  strided loads ~4 cycles per instruction, ~2.5x a unit-stride load). The design keeps strided segment accesses to
  the `ido == 1` / `i = 0` columns and to "mode B" (`design.md` section 2.4), but their share should be measured on
  the board with `perf stat` (cycles and instructions, `hardware-run-guide.md` section 4).
* Large transforms become memory-bound (juFFTe reports this for SG2044 in particular); the 2^20 points
  (16 MB in + 16 MB temp) will show a smaller cycle gain than the count gain.
* QEMU wall-clock time is meaningless (TCG emulates each vector instruction with a per-element helper, so the RVV
  binary is *slower* in wall time than the scalar one). No timing from QEMU appears in this report.

The three-tier protocol therefore is: QEMU counts (this report) -> board cycles/time (`hardware-run-guide.md`,
section 8 below) -> x86/ARM counterparts with the same harness (section 6).

Reading the table:

* **Baseline choice.** The speed-ups are against the same compiler's `rv64gc` scalar build. The leanest scalar
  build of either compiler is GCC's (pure scalar `rv64gc`: 283,411 for the n = 4096 kernel; auto-vectorised
  `rv64gcv`: 283,152, `docs/data/kernel_insns_remeasured.txt`); against it the clang RVV build is still 4.1x at
  VLEN 256 (283,411 / 69,525) and 2.1x / 7.9x at VLEN 128 / 512, so the conclusion does not depend on the baseline.
* **Scaling with VLEN is close to linear from 128 to 256 and from 256 to 512** (e.g. n = 65,536: 2.83 M -> 1.42 M
  -> 0.72 M). This is the point of the vector-length-agnostic design: the same binary halves its instruction count
  every time VLEN doubles, with no VLEN-specific code, no `-mrvv-vector-bits`, and no recompilation (the upstream
  generic-vector path is frozen at 256 bits and crashes at other VLENs when built with `-mrvv-vector-bits=zvl`,
  `related-work.md` section 2).
* **Small n gains less.** n = 256 is 2.8x at VLEN 256 and 3.7x at VLEN 512: the last radix passes have
  `ido` and `l1` smaller than the vector length (partial vectors, `vsetvl` tails), and per-pass fixed costs
  (address set-up, the `i = 0` column) are not amortised. Below n ~ 64 the scalar path is competitive; the
  dispatch could fall back to it (open item, `design.md` section 7).
* **n = 2^20 gains less than n = 2^16** (3.8x vs 4.8x at VLEN 256). Per element and pass the RVV path spends 3.6
  instructions at 2^16 and 5.1 at 2^20 while the scalar path spends 17.5 and 19.6. The cause has not been isolated
  yet (candidates: the extra radix-8 pass of 2^20 = 8^6 * 4 running at LMUL 1, and the mode-A twiddle vectors
  being re-loaded for every `k`); it is listed as follow-up work in `design.md` section 7. On hardware this size is
  memory-bound anyway.
* **float vs double.** With half the element size a vector holds twice the lanes, so float gains roughly twice
  as much relative to double at the same VLEN (kernel n = 65,536 at VLEN 256: 4.8x double, 9.6x float; API without
  cache: 5.2x / 8.7x, section 2), as long as the scalar baseline costs the same per element, which it does for
  pocketfft.

The independent re-measurement of section 9 (`docs/data/kernel_insns_remeasured.txt`, commit `2e99710`, i.e. with
the attribute) shows where GCC still loses: on power-of-two lengths GCC is 1.3-1.4x clang (n = 4096: 96,171 vs

report with `work/p4_gcc.s`-style reproducers).

The picture at the public-API level is more balanced (table above): GCC's scalar code (plan construction, copies,
the scalar `rv64gc` builds themselves) is 5-15 % leaner than clang's, so for `r2c`/`c2r` and for n = 1024 GCC's RVV
binaries execute *fewer* instructions than clang's (0.67-0.9x), while for the complex passes clang stays ahead
(kernel 1.34-1.39x, `c2c` with plan cache 1.2-1.4x). Both compilers deliver the full speed-up over their own scalar
build for real transforms (section 2: GCC 5.7-5.8x, clang 5.7-5.8x at VLEN 256 for double r2c/c2r without cache).

Recommendation: build with clang >= 19 (clang 23 used here) when complex transforms dominate; GCC 14/15 is supported,
correct, on par or better for real transforms and small sizes, and costs roughly 1.4x the instructions of clang on
power-of-two complex kernels after the attribute (more on radix-5 lengths). The remaining gap is a GCC
register-allocation issue around RVV tuple types that is worth a GCC bug report (follow-up in `design.md` section 8).

## 8. Reproducing and extending the measurement

QEMU (this report):

```sh
scripts/build.sh                                   # build/<variant>/fft_check and fft_bench for all variants

scripts/measure_all.sh && scripts/measure_rest.sh  # the full matrix -> results/final_insns.csv (~45 min)
scripts/run_bench_qemu.sh --quick                  # fft_bench-based sweep incl. vector-instruction share -> results/bench_qemu.csv
scripts/run_bench_xisa.sh                          # x86-64 native ns + x86/aarch64/riscv64 counts -> results/bench_xisa.csv
python3 docs/gen_tables.py                         # regenerate the tables of this file
```

Board (`docs/hardware-run-guide.md` sections 2-6 give the prerequisites, pinning, governor and `perf` details):

```sh
# correctness gate first (same binaries, FFTW reference built scalar)
taskset -c 2 build/riscv64-clang23-rvv/fft_check --label board --csv board_correctness.csv
# time per transform (median of >= 5 launches, >= 0.5 s each), scalar and RVV binaries
for b in riscv64-clang23-scalar riscv64-clang23-rvv; do
  taskset -c 2 build/$b/fft_bench --type double --kind c2c-fwd --n 4096 --mode plan --trials 11
done
# cycles and instructions: perf stat on N and 2N repetitions, difference / N (validates the QEMU counts)
perf stat -e cycles,instructions -r 5 taskset -c 2 build/riscv64-clang23-rvv/fft_bench --type double --kind c2c-fwd --n 4096 --reps 200 --trials 1
perf stat -e cycles,instructions -r 5 taskset -c 2 build/riscv64-clang23-rvv/fft_bench --type double --kind c2c-fwd --n 4096 --reps 400 --trials 1
```

Report per machine: board/SoC, kernel, ISA line, VLEN (printed by `fft_bench`), governor and frequency, compiler
and flags, then per (type, kind, n): ns/transform scalar and RVV, speed-up, cycles and instructions per transform,
IPC, and GFLOP/s by the `5 n log2 n` (c2c) / `2.5 n log2 n` (r2c, c2r) convention. The instruction counts from
`perf` should match the QEMU counts within the libc/kernel noise; the cycle ratio is the real speed-up.
